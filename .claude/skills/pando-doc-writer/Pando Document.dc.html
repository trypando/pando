1Summary

Every app on Pando builds in its own short-lived environment and runs in its own sandbox. Apps on the same host can't read each other's files, processes or network traffic. Variables you mark as secret are encrypted at rest and only decrypted inside the running app.

This paper describes those boundaries in plain terms, so you can decide whether Pando fits your own security requirements.

2Scope

This paper covers apps deployed through Pando on hosts you connect. It doesn't cover the security of your own code, its dependencies, or services your app calls.

Apps run only on hosts you connect. App code and data stay on those hosts.

3Build isolation

Each build starts from a clean image with no network access to other apps. When the build finishes, the environment is discarded and only the built artifact is kept.

3.2 Network access during builds

Builds can reach public package registries and nothing else. They can't reach your other apps, the host's private network or the Pando control plane.

4Runtime isolation

Each running app gets its own sandbox with a private filesystem, its own process tree and a dedicated network namespace. Traffic between apps on the same host goes through the public URL, the same as traffic from anywhere else.

Apps can be restarted, stopped or redeployed from the console. Their memory and the files they write while running aren't readable from outside the sandbox.

6Reporting a vulnerability

Email security@pando.dev using this format. Pando replies within two working days.

Subject: Vulnerability report: build logs expose secrets

App URL:   https://notes-7f3a.pando.app
Steps:     1. Add a secret named API_KEY
           2. Trigger a deploy
           3. Open the build log
Expected:  API_KEY is masked
Actual:    API_KEY appears in plain text on line 42
